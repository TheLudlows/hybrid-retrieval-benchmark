# TaurusDB 真实文档试测

WeKnora Lite 与 ContextBase 分别导入同一份 40 篇官方文档，运行 40 道题。其中 34 道有证据、10 道跨文档、6 道无答案。两边使用原有的完整混合检索、相同的 BGE-M3 和 BGE Reranker v2 M3，并以同一个词表计算正文预算。测量环境为同一台 CPU 机器上的本地模型服务。

| 指标 | WeKnora Lite | ContextBase |
| --- | ---: | ---: |
| 证据召回 @256 正文 Token | 46.1% | 41.2% |
| 证据召回 @512 正文 Token | 52.9% | 64.2% |
| 证据召回 @2,000 正文 Token | 76.0% | 89.2% |
| 证据 Hit@5 | 33/34 | 30/34 |
| 跨文档完整命中 @2,000 正文 Token | 3/10 | 5/10 |
| 串行查询 p95（秒） | 13.85 | 13.48 |
| 并发 8 查询 p95（秒，成功请求） | 155.70 | 148.29 |
| 并发 8 完整检索成功数 | 38/40 | 40/40 |
| 入库平均输入 Token/篇 | 1,609 | 1,561 |
| 查询平均输入 Token/题 | 19,491 | 19,606 |
| 更新后首次看到新证据（秒，中位数） | 27.55 | 11.63 |
| 更新后首次未返回旧证据（秒，中位数） | 12.48 | 11.63 |

两边串行都成功完成 40 道题。WeKnora 并发 8 有两次重排连接被重置，按完整链路失败计数。模型输出 Token 均为 0。两边 6 道无答案题均返回候选。ContextBase 有两条候选缺少来源正文，位于第 28 和 29 条，按原生返回计分。

按逐题证据计数，WeKnora 在 2,000 Token 下遗漏的 15 条证据都在预算外的原生正文里。ContextBase 有 5 条在预算外、3 条未出现在原生正文里。

两边 5 组文档更新均确认了新证据已出现、旧证据在该轮未返回。轮询间隔为 2 秒，记录从提交更新到查询返回的时间，因此包含完整混合检索耗时。更新样本在质量和负载测量后加入各自的试测库。

TaurusDB 原文来自 [官方页面快照构建](https://github.com/TheLudlows/hybrid-retrieval-benchmark/actions/runs/42977214079)。构建时以抓取的正文为准，将自动备份保留期标注修正为 1–3660 天，并重新校验全部证据。结果目录保留语料哈希、逐题证据命中、模型调用、负载和更新记录。实际正文可由官方快照重建。

- WeKnora Lite 源码提交 `cbdcebabf48c5ee2d6868b370326aa8341703f62`。
- ContextBase 源码提交 `c1cc16269361f2ed0ff4d1cfcb20345137b3b820` 加基线中的配置读取修正。
- 向量和重排模型沿用基线的固定版本。ContextBase 使用 PostgreSQL 18.4、pg_search 0.24.1 和 jieba。

## 复跑入口

使用基线相同的本地产品和模型运行时。先构建并验标 TaurusDB 语料，再从仓库根目录执行。

```bash
BENCH_DATASET_DIR="$PWD/taurusdb-pilot-corpus" BENCH_LOAD_CONCURRENCY=8 \
  deployment/api-venv/bin/python deployment/run_full_hybrid.py weknora contextbase
```

运行器按文档和查询记录模型调用，保留原生前 5 条的证据命中。串行质量查询作为并发 1 的延迟样本，并发 8 使用同一题集单独执行。归档的逐题记录包含证据 ID、正文预算命中和延迟。
