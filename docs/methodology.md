# 文档召回测试方法

## 工作负载和配置

- 建立两个独立试测库，向 WeKnora Lite 和 ContextBase 导入同一份语料。记录源文件哈希、入库完成状态、分块数、模型版本和产品提交。
- WeKnora Lite 使用原生 `POST /api/v1/knowledge-search`，开启向量、中文关键词和重排。ContextBase 使用原生 `Recall` 及 `include.chunks`，开启向量、中文 BM25、图、时间和重排。
- 使用相同的 BGE-M3 和 BGE Reranker v2 M3。保留原生候选合并及正文返回方式。通过 trace 或模型请求日志验证配置实际生效，记录各查询的候选数。
- 使用同一组查询及固定顺序。保留原生返回排序、文档 ID、证据所在正文、请求耗时和模型调用用量。对出错题单独计数。
- 测试集包括精确定位、语义改写、相似版本或环境、跨文档和无答案。题目按正确文档 ID 和原文标证据。扩充正式题库时按文档族留出，避免把调参题的改写版用于出分。

## 指标

| 指标 | 计算方法 |
| --- | --- |
| 同等正文预算下的证据召回 | 按返回顺序拼接正文，使用统一 tokenizer 截断到 2,000 Token。每题以命中的必需证据数除以该题必需证据数，对有答案题取平均。同时报告 256 和 512。 |
| 证据 Hit@5 | 检查原生顺序前 5 条返回，只要有一条包含该题标注证据就算命中。报告分母为有答案题数。归档基线脚本另含按正确来源文档计算的文档 Hit@5。 |
| 跨文档完整命中 | 对需要至少两篇不同文档的题，在同一正文预算内找齐所有必需证据才算命中。 |
| p95 检索延迟 | 相同硬件、模型服务、负载和超时配置下，按固定并发分别报告 p95、超时率和错误率。历史基线为本地 CPU 串行测试，包含重排。 |
| 模型 Token | 记录每篇文档及每次查询的模型输入、输出，按 Embedding 和重排分别汇总。模型端计数与返回正文的预算分开。历史入库结果按整批记录。 |
| 更新后可检索时间 | 以提交同一文档 ID 的 V2 更新为起点。用固定间隔和查询测量新证据首次出现及旧证据停止出现的时间。 |
| 无答案题行为 | 分开统计是否返回候选，以及是否返回不适用的证据。 |

## 复现范围

`doc_recall_v1/bench.py` 提供原生 API 采集和合成基线打分。`deployment/run_full_hybrid.py` 是该次本地实测的入口，依赖预装的 Python 环境、产品源码或二进制、PostgreSQL 运行时和模型文件。路径及配置在脚本中记录。直接验证已保存的运行结果可用 `deployment/summarize_full_hybrid.py`。

TaurusDB 题集是下一轮试测输入。更新测试和固定并发负载需要按上表单独执行，历史基线结果只代表当次测量。
